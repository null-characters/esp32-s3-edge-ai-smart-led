# ESP32-S3 Edge AI 网关 v5 总体规划：家电小精灵 (Embodied Agent) 升级

## 1. 核心愿景与架构演进

在 v3 版本中，项目实现了从"感知设备"到"交互设备"的跨越，利用 ESP-SR 框架实现了本地唤醒与 50+ 条离线命令词控制。
v5 版本将定位为"前沿探索与具身智能（Embodied AI）升级"。本项目将剥离单片机本地算力瓶颈，通过局域网接入高性能边缘计算节点（X99 + Tesla P4 算力服务器），利用大语言模型（LLM）实现真正意义上的自然语言交互、情感化光影表达与主动式环境响应。

### 1.1 核心架构变动

* **废弃：** 移除 v3 中的 `MultiNet`（命令词识别模块），摆脱僵化的预设指令束缚。
* **保留与强化：** 保留 `WakeNet` (唤醒词) 与 `VAD` (语音活动检测)，确保零延迟唤醒与极低待机功耗。保留现有的多模态感知能力（LD2410 毫米波雷达、TFLM 声音分类器）。
* **新增：** 引入全双工/半双工的音频流传输层（WebSocket），以及设备状态同步总线（MQTT）。
* **新增：** Opus 音频编解码层叠加在 WebSocket 之上，将原始 PCM (256kbps) 压缩至 ~24kbps，减少 Wi-Fi 拥塞风险。
* **新增：** **本地降级模式 (Fallback Mode)** ——保留少量硬编码本地命令（关灯/调亮/调暗），当边缘服务器不可用时自动降级。
* **新增：** **多轮会话管理 (Conversation Manager)** ——Agent Backend 维护对话历史，支持上下文关联的自然语言交互。

## 2. 系统组件划分

v5 版本的系统将彻底分为"端（感官与执行）"**与**"边（认知与决策）"两个物理节点：

### 2.1 端侧：ESP32-S3 (感官与执行终端)

专注于高质量的数据采集、极低延迟的传输以及物理声光效果的渲染。

* **音频前端：** 依赖 `AEC` 与 `VAD` 提取干净的人声切片。
* **流式通信：** 唤醒后，通过 WebSocket 将音频切片推送到边缘服务器，并接收服务器下发的流式音频（TTS）进行播放。
* **光影渲染引擎：** 接收 JSON 格式的控制指令，解析情感标签（Emotion Tag），驱动 LED 执行特定的光影动画（如：开心->青色呼吸；思考->橙色流水）。

### 2.2 边侧：X99 Edge Server (认知大脑中枢)

部署在局域网内的高性能 Ubuntu 节点，承载"家电小精灵"的人格与记忆。

* **语音管线 (Voice Pipeline)：** 基于 `Faster-Whisper` 实现极速 STT，基于 `Piper` 实现自然流畅的流式 TTS。
* **大模型引擎 (LLM Engine)：** 运行基于 `Ollama` 的 `Qwen2.5-7B` (GGUF量化格式)，提供强大的语义理解与指令生成能力。
* **智能体中控 (Agent Backend)：** 基于 Python/FastAPI 构建。统一承载 WebSocket 音频流、MQTT 消息路由、STT/LLM/TTS 编排。维护系统级 Prompt（家电小精灵人设），管理多轮对话历史（Conversation History），并将 LLM 的自然语言解析为可被 ESP32 执行的设备控制 JSON。

## 3. 阶段实施路线图 (Roadmap)

### 阶段一：边缘认知基建搭建 (Server-Side Infra)

* **目标：** 跑通边缘服务器的 AI 基础管线。
* **任务项：**
  * 组装 X99+P4 硬件，部署 Ubuntu Server 22.04 LTS 及 Docker 环境。
  * 部署 Ollama 并测试 Qwen 7B 模型推理性能。
  * 部署 STT 与 TTS 服务，并对外暴露内部 RESTful API。
  * 编写中控测试脚本：输入一段 .wav 录音，能输出大模型的 TTS 音频响应。

### 阶段二：通信总线与协议定义 (Protocol Definition)

* **目标：** 建立端与边之间的标准化对话渠道。
* **任务项：**
  * 搭建 MQTT Broker (Mosquitto)，定义设备状态上报 Topic（如 `node/room/radar/status`）与指令下发 Topic。
  * 定义基于 WebSocket 的音频流媒体传输帧结构。
  * 设计 LLM Function Calling 的 JSON 协议结构（包含文本、控制参数、情感标签）。

### 阶段三：ESP32-S3 固件重构 (Firmware Upgrades)

* **目标：** 改造现有的 v3 固件，接入云端大脑。
* **任务项：**
  * 从 ESP-SR 中剥离 `MultiNet`，保留 `WakeNet`。
  * 开发 WebSocket 客户端，实现 VAD 触发后的音频流式上行传输。
  * 升级 `command_handler.c`：从处理本地枚举指令，改为解析来自 MQTT 的复杂 JSON 动作序列。
  * 扩展 `led_pwm.c`：引入基于情感（Emotion）的光效动画库（呼吸、闪烁、律动）。

### 阶段四：多模态融合与主动交互 (Proactive Agent)

* **目标：** 利用既有传感器，实现更拟人的智能体验。
* **任务项：**
  * **雷达触发对话：** 当 LD2410 雷达 探测到用户进入房间且停留，通过 MQTT 触发大模型主动发起问候（"欢迎回来，需要开灯吗？"）。
  * **场景声学联动：** TFLM 声音分类器 识别到"键盘敲击声"，将该状态作为上下文放入大模型 Prompt，大模型自动调整灯光为"专注模式"并配合相应语音提示。

## 4. 关键技术瓶颈与缓解策略

| 技术难点 | 潜在风险 | 应对策略 |
| --- | --- | --- |
| **端到端延迟 (E2E Latency)** | 从录音到播音的链路过长，延迟若超过 3 秒会破坏交互的自然感。 | 采用**全流式架构 (Streaming)**。STT 切片识别，LLM 打字机输出流式触发 TTS。追求首字响应时间 (TTFT) < 1.5 秒。 |
| **音频数据网络抖动** | 局域网 Wi-Fi 信号不稳定导致音频断续。 | 在 ESP32 上实现基于 PSRAM 的环形缓冲区 (RingBuffer)，增加抗抖动阈值。前端增加 Opus 编码 (24kbps)，降低带宽占用。 |
| **LLM 幻觉控制** | 大模型输出错误的 JSON 格式，导致 ESP32 解析崩溃。 | 在 Agent Backend 强制启用 JSON Mode 约束输出，并增加 JSON Schema 校验层，格式错误自动请求重试。 |
| **多设备唤醒冲突** | 若未来增加多个 ESP32 节点，唤醒词可能同时被多个设备响应。 | 基于 MQTT 在中控端实现"唤醒选主"逻辑（根据各节点的音频能量值确定单一响应设备）。 |
| **单点故障 (Server Dependency)** | 边缘服务器宕机/断连后，设备完全失智。 | 保留本地降级模式（Fallback Mode），硬编码关灯/调亮/调暗等基础命令，检测到 WebSocket 连接失败后自动降级。 |
| **多轮对话缺失上下文** | 用户说"再亮一点"，Agent 不知"再"指什么。 | Agent Backend 添加会话管理器 (ConversationManager)，维持最近 N 轮消息作为 LLM Chat History。 |
| **TTS 与麦克风冲突** | TTS 播放时用户说话，两路音频混叠。 | 固件实现音频优先级管理：Mic（用户语音）> 本地提示音 > TTS。检测到唤醒词/用户说话时自动静音 TTS。 |
| **PCM 原始音频带宽过高** | 256kbps 上行在 Wi-Fi 干扰下易丢包断流。 | WebSocket 帧内叠加 Opus 编解码层，将带宽降至 ~24kbps，并提升抗丢包能力。 |

## 5. 与 v4 规划的关系

v5 规划与 v4（云端智能体）形成互补：

| 维度 | v4 云端智能体 | v5 边缘智能体 |
|------|-------------|-------------|
| 部署形态 | 云端API服务 | 局域网边缘服务器 |
| LLM方案 | 云端API调用 | Ollama + Qwen2.5-7B 本地部署 |
| STT方案 | 云端API | Faster-Whisper 本地部署 |
| TTS方案 | 云端流式TTS | Piper 本地部署 |
| 通信协议 | HTTPS API | WebSocket + MQTT |
| 适用场景 | 需要云端扩展能力 | 隐私优先、低延迟、离线可用 |

**建议**：v5 可作为 v4 的"边缘优先"变体，两者可共存，根据网络条件自动切换。
